# Releasing Sonora

Publishing a GitHub release with a tag like `v1.2.0` runs
`.github/workflows/release.yml`. The tag sets the version
(`tools/setversion.sh` writes it into `giode.toml`, the build number is the
workflow's run number). The workflow tests, builds every package and
attaches them to the release.

The workflow is hand-written, not generated by `giode ci`: the archives
are built with `go build` (so Windows gets Sonora's own resources from
`cmd/sonora/winres`), Linux is built for arm64 too, and Android needs the
sherpa-onnx libraries that `tools/fetchsherpa` downloads. It uses the same
secret names as `giode ci`'s workflow, so the steps below match the other
Giode apps.

| Where | What the release gets | Needs |
| --- | --- | --- |
| GitHub, Windows | `sonora-<tag>-windows-amd64.zip`, `-arm64.zip` | nothing |
| GitHub, macOS | `sonora-<tag>-darwin-arm64.zip`, `-amd64.zip` (ad-hoc signed) | nothing; users must clear the quarantine flag |
| GitHub, macOS | `sonora-<tag>-macos-universal.dmg`, signed and notarized | a Developer ID certificate and the notary secrets; without them the job is skipped |
| GitHub, Linux | `sonora-<tag>-linux-amd64.tar.gz`, `-arm64.tar.gz` | nothing |
| GitHub, Android | `sonora-<tag>-android.apk` | the release keystore, or it is signed with a throwaway key |
| Google Play | `sonora-<tag>-android.aab` | the release keystore secrets (no bundle without them) |
| Microsoft Store | `sonora-<tag>-windows-amd64.msix`, `-arm64.msix` | a Partner Center account and the reserved name |

**Not released to:**

- **Mac App Store.** Every Mac App Store app runs in the App Sandbox, and
  Sonora's desktop engines are Python programs it installs at run time: it
  downloads `uv`, a Python interpreter, PyTorch and each engine's packages,
  then runs them as child processes. The sandbox won't execute programs an
  app downloads into its container (they're quarantined), and App Review
  guideline 2.5.2 forbids downloading or running code that adds features.
  Without them the store version would keep only the system voices and API
  servers the user runs elsewhere; the on-device sherpa-onnx engines aren't
  built for macOS. That isn't Sonora. macOS users get the notarized `.dmg`.
- **Apple App Store (iOS).** iOS isn't one of Sonora's platforms
  (`app.platforms` in `giode.toml`). On iOS the build has no on-device
  engines (there are no sherpa-onnx libraries for iOS in the build) and no
  recording (`internal/audio/record/capture_mobile.go` is a stub), so it
  would only talk to API servers the user runs elsewhere, which App Review
  rejects as minimum functionality (guideline 4.2). The `[ios]` sections
  stay in `giode.toml` for a future port.
- **Snap Store / Flathub.** Linux users download from the GitHub release.

Sonora has no `LICENSE` file yet. Microsoft and Google don't require one,
but add one before publishing if the source is meant to be open, and keep
the third-party credits in the README (each model has its own license,
shown on its engine card).

## Repository secrets

Set these in GitHub under Settings → Secrets and variables → Actions. Each
`*_BASE64` secret is the file encoded with `base64 -i file | pbcopy` on
macOS, or `base64 -w0 file` on Linux. Without a secret, that step is
skipped (or uses a throwaway key) and the rest of the release still builds.

| Secret | What it is |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64`, `GIODE_KEYSTORE_PASS` | The Android release keystore and its password: signs the APK and the Play bundle (the upload key with Play App Signing). The older `ANDROID_KEYSTORE` and `ANDROID_KEYSTORE_PASSWORD` names still work. |
| `MACOS_CERT_BASE64`, `MACOS_CERT_PASS` | The "Developer ID Application" certificate as a `.p12`, and its password: signs the `.dmg` |
| `GIODE_NOTARY_ID`, `GIODE_NOTARY_TEAM_ID`, `GIODE_NOTARY_PASS` | Your Apple ID, team ID and an app-specific password: notarizes the `.dmg` |

The Microsoft Store packages need no secret: Partner Center signs them.

## Android and Google Play

The APK and the bundle are built by `giode build -release android aab`.
Two settings in `giode.toml` matter here:

- **`target_sdk = 36`.** Google Play requires Android 16 (API 36) for new
  apps and updates since 31 August 2026; the CLI's default (35) is
  rejected. The workflow installs `platforms;android-36` to match. Test
  the release on an Android 16 device or emulator before the first upload.
- **`application_attributes = { enableOnBackInvokedCallback = "false" }`.**
  Gio handles Back in `onBackPressed()`, which Android 16 no longer calls
  for apps targeting 36 (predictive back). The opt-out keeps Back closing
  dialogs and returning to the Studio. **Test the back gesture on an
  Android 16 device**: open a dialog, swipe back (it should close), then
  swipe back from another page (it should return to the Studio, not exit).
- **`keystore = "release.keystore"`.** `giode build -release` refuses to
  run without `android.keystore`. The workflow writes `release.keystore`
  from `ANDROID_KEYSTORE_BASE64` and passes the password in
  `GIODE_KEYSTORE_PASS`. The file is in `.gitignore`; never commit it.

`android.libraries` points at `third_party/sherpa-onnx/android.aar`, which
`go run ./tools/fetchsherpa android` writes. giode packs its libraries
beside `libgio.so` in the APK and the bundle; the workflow runs
`fetchsherpa` before building. (`tools/packapk` isn't needed any more for
these builds.)

1. Create the upload keystore once, and keep it and its password safe
   (Play only accepts uploads signed with it):

   ```sh
   GIODE_KEYSTORE_PASS='a long password' giode keystore
   base64 -w0 release.keystore   # paste into ANDROID_KEYSTORE_BASE64
   ```

   If releases were already signed with a key from the old
   `ANDROID_KEYSTORE` secret, keep using that keystore, so APK updates
   still install over earlier versions.
2. Add `ANDROID_KEYSTORE_BASE64` and `GIODE_KEYSTORE_PASS`.
3. In the Play Console, create the app: name **Sonora**, app (not game),
   free. The package name is `com.sonora.app` (`app.id`); it can never
   change after the first upload.
4. Use **Play App Signing** (the default): Google keeps the app signing
   key and the keystore above is the upload key. Upload the first bundle
   in a test track (internal testing first).
5. Publish a release; download `sonora-<tag>-android.aab` from it and
   upload it in the Play Console.
6. Fill in App content:
   - **Privacy policy:** https://xmhrnx.github.io/sonora/#privacy
   - **Data safety:** see below.
   - **Foreground service permissions:** Sonora declares a `dataSync`
     foreground service (`android.keep_alive`): it keeps speech
     generation, transcription and model downloads running when the user
     switches apps, and shows a notification while it runs. Play asks for
     a short description and a video of the feature (start a long
     transcription, switch apps, show the notification). Android 15 and
     later limit `dataSync` services to about 6 hours a day.
   - **Ads:** no ads.
   - **Content rating:** see below.
   - **Target audience:** 13 and over (or 18 and over); not designed for
     children.
7. Store listing: the copy below, the icon, a feature graphic and phone
   screenshots.

## Microsoft Store

1. Open a Partner Center developer account (the one EasySend and AnyFile
   use: publisher `CN=B40E8F57-A7E0-40BB-8E74-5D051D0B578B`, display name
   Mehran Zahiroddini).
2. Reserve the name **Sonora**.
3. On the product's Product identity page, check the values against
   `[windows.msix]` in `giode.toml`:
   - **Package/Identity/Name** → `identity_name` (now
     `MehranZahir.Sonora`; change it if Partner Center shows another).
   - **Package/Identity/Publisher** → `publisher`.
   - **Package/Properties/PublisherDisplayName** →
     `publisher_display_name`.
4. Commit and publish a release. Upload `sonora-<tag>-windows-amd64.msix`
   and `sonora-<tag>-windows-arm64.msix` in one submission. The Store signs
   them.
5. Sonora is a full-trust desktop app. When the submission asks why it
   uses `runFullTrust`, explain: it installs speech engines (Python
   environments made with uv) in its data folder and runs them, and runs
   command-line engines the user adds.
6. Add the privacy policy URL, the listing below, and screenshots.

**In the Store package:** the data folder (`%LOCALAPPDATA%\Sonora`:
engines, models, Python environments, clips) is redirected into the
package's own storage, so it is removed with the app and not shared with
a zip copy of Sonora. The "Transcribe with Sonora" and "Read aloud with
Sonora" Explorer entries come from the package (`context_actions`), not
from the zip build's registry entries. Test installing a large Python
engine (IndexTTS or Chatterbox) from the Store build before the first
submission: deep virtualenv paths in the package's redirected folder are
the likeliest thing to break.

## macOS (GitHub)

1. Join the Apple Developer Program.
2. Create a "Developer ID Application" certificate, export it with its key
   as a `.p12`, and add `MACOS_CERT_BASE64` and `MACOS_CERT_PASS`.
3. Create an app-specific password for your Apple ID and add
   `GIODE_NOTARY_ID`, `GIODE_NOTARY_TEAM_ID` and `GIODE_NOTARY_PASS`.
4. Publish a release; it gets `sonora-<tag>-macos-universal.dmg`, which
   opens without the quarantine workaround. Once it does, the README's and
   the website's "isn't notarized yet" notes can go, and the website's
   macOS card can point at the `.dmg`.

**Data safety (Play) and Microsoft's privacy questions:**

- Data collected: **none**. Sonora sends nothing to its developer: no
  analytics, crash reports, accounts or ads.
- Data shared: **none**. Text or audio goes to a third party only when the
  user adds an API server and sends to it, which is a user-initiated
  transfer to a service the user chose.
- Microphone: used only while the user records; the recording stays on the
  device.
- Data deletion: everything is local; uninstalling removes it.

**Export compliance:** Sonora uses only standard HTTPS through the OS and
Go's standard library (`ITSAppUsesNonExemptEncryption = false` is set for
macOS). Microsoft and Google: no export-controlled encryption.

## Before the first store upload

- `go vet ./...` and `go test ./...` pass; `giode build msix` packs
  locally.
- An Android 16 device or emulator runs the APK from the release: install
  an on-device engine, generate, record, transcribe, leave a long job
  running in the background, and check the back gesture (see above).
- The Store MSIX installs on Windows (sideload it with
  `Add-AppxPackage -AllowUnsigned` from an admin PowerShell, Windows 11
  with developer mode), installs a Python engine and generates speech.
